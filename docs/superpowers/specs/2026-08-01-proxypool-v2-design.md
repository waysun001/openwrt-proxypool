# ProxyPool V2 重构设计

日期：2026-08-01
状态：已完成需求确认，待最终文档审阅
目标平台：OpenWrt 23.05.3，GL-MT6000（mediatek/filogic）

## 1. 背景

ProxyPool 用于把连接到 OpenWrt 路由器的终端绑定到指定的 L2TP、SOCKS5 或 SLP 节点。系统最多保存和运行 60 个节点，常见规模为 40～50 个，其中 L2TP 是主要协议。

当前实现由 LuCI、Shell 脚本、watchdog、PPP 回调和协议进程共同修改运行状态，已经出现以下系统性问题：

- 浏览器中的“顺序连接”只等待后台启动命令返回，没有等待节点真正连接，批量启动实际会重叠执行。
- 防火墙锁超时后会被其他进程删除，多个重建过程可能同时清理路由或规则。
- L2TP 接口或进程存在但没有获得地址时，watchdog 会永久认为节点仍在连接。
- 配置删除和停止顺序不一致时，可能无法判断节点类型并遗留进程。
- PPP 回调、防火墙重建和 watchdog 之间缺少单一所有者，存在丢事件和状态覆盖。
- DNS 没有严格按设备和节点隔离，可能从本地主 WAN 解析。
- 当前防火墙显式允许部分局域网私有地址访问，与终端隔离要求相反。
- 有线端口与无线客户端缺少完整的二层隔离。
- `max_clients` 只是配置项，没有形成真实容量和导入限制。

这些问题不是单个补丁能够可靠解决的，因此采用分阶段的控制面重构。

## 2. 已确认需求

### 2.1 核心行为

- 一个节点可以绑定多个终端。
- 终端先通过 DHCP 接入一次，系统自动发现其 MAC、当前 IP 和主机名；用户不手工输入 MAC。
- 绑定后系统自动创建稳定 DHCP 租约，MAC 是设备身份，固定 IPv4 是管理地址。
- 未绑定设备只能访问路由器管理页面和必要的路由器基础服务，不能访问互联网。
- 已绑定设备只能通过指定节点访问互联网，任何情况下都不能回退到本地主 WAN。
- 节点离线、服务崩溃、路由器启动中、防火墙重载或配置不完整时一律 fail closed，即保持终端断网。
- 所有普通终端禁止互相访问，包括 LAN 口、有线与无线、同一无线和不同无线之间。
- 普通终端可以访问 LuCI 管理页面。
- SOCKS5 和 SLP 第一阶段只支持 TCP；客户端外部 UDP 一律阻断。
- L2TP 控制流量以及 SLP 使用 QUIC 时的隧道承载流量不属于“客户端 UDP”，只允许路由器自身发送到配置的精确节点地址/端口。
- 第一阶段正式支持 IPv4，阻止客户端 IPv6 转发和 IPv6 旁路。

### 2.2 规模和平台条件

- 节点硬上限为 60，常见在线规模为 40～50。
- L2TP 使用 OpenWrt netifd 与 xl2tpd。
- 采用一个由 procd 管理的共享 xl2tpd，为每个 L2TP 节点创建独立 netifd 接口。
- 用户确认没有一个物理 LAN 口下接交换机并挂多个终端，因此可以使用 DSA bridge port isolation 隔离各物理端口。
- 用户可以配合四轮真机测试，主动操作总时间预计 2～3 小时，另有 12～24 小时被动稳定性观察。

### 2.3 非目标

- 第一阶段不保证微信语音、视频、游戏、QUIC 或其他依赖 UDP 的功能。
- 第一阶段不提供客户端 IPv6 上网。
- MAC 用作稳定的运维身份，不是密码学身份。防护恶意 MAC 仿冒需要 802.1X、独立 VLAN 等额外机制，不属于本次范围。
- 不在第一阶段实现任意下游交换机拓扑中的端口级终端隔离。

## 3. 总体架构

### 3.1 期望状态与运行状态分离

UCI 只保存持久化的期望状态：

- 全局配置；
- 节点定义；
- 设备定义；
- MAC、固定 IP 与节点绑定；
- 是否启用；
- 配置模式版本。

新增常驻服务 `proxypoold`，由 procd 启动和拉起。它是运行状态的唯一所有者，负责：

- 串行接受配置和控制命令；
- 驱动 netifd、共享 xl2tpd、SOCKS5/SLP 适配器；
- 创建并原子更新 nftables 集合、策略路由和节点映射；
- 维护连接状态机、任务队列、超时和重试；
- 提供按节点隔离的 DNS 服务；
- 从系统实际状态恢复并与 UCI 期望状态对账；
- 输出结构化状态、事件和诊断信息。

LuCI、批量导入、watchdog 替代逻辑、PPP up/down 回调均不得直接创建进程、清理接口、修改路由或重建防火墙。PPP 和 netifd 事件只通知 `proxypoold`，由它判断事件是否仍属于当前配置代次。

### 3.2 实现语言和接口

`proxypoold` 建议使用 Go 编写并为目标平台交叉编译。选择 Go 的原因是状态机、超时、并发队列、结构化协议和单元测试比继续扩展 Shell 更可靠，GL-MT6000 的资源也足以运行单个常驻二进制。

控制接口使用仅本机可访问的 Unix domain socket，例如 `/var/run/proxypoold.sock`，消息采用有版本的 JSON。`proxypoolctl` 是 LuCI 和诊断脚本使用的薄客户端。Socket 由 root 管理并设置严格权限，不监听 LAN TCP 端口。

所有写操作由 daemon 验证、持久化并增加配置 revision。LuCI 只负责展示、输入校验提示和提交命令，不把用户字段拼接为 Shell 命令。

### 3.3 单写者原则

运行期只允许 `proxypoold` 修改 ProxyPool 拥有的：

- nftables 表、链、集合和映射；
- 策略路由表与规则；
- 动态 netifd L2TP 接口；
- 协议子进程；
- 本地代理与 DNS listener；
- ProxyPool 运行目录。

基础 fail-closed 规则属于 OpenWrt 持久防火墙配置，即使 daemon 没有启动也生效。daemon 只能在这些基础拒绝规则之上增加精确、可撤回的节点通道。

## 4. 数据模型

配置模式版本为 V2。

### 4.1 全局配置

至少包含：

- `schema_version=2`；
- 服务总开关；
- `max_nodes=60`，不可由页面设置为更大；
- 管理页面允许的 LAN 地址和 TCP 端口，默认读取路由器 LAN IPv4 并允许 80/443；
- L2TP 启动并发，默认 4，可在验证后调整到 3～5；
- 其他协议启动并发；
- 连接、停止和健康检查超时；
- 重试上限和退避参数；
- 一个或多个可配置 DoH 上游及其 bootstrap 地址。

### 4.2 节点

每个节点具有不可变的内部 ID，显示名称可以修改。公共字段包括：

- ID、名称、协议类型、启用状态；
- 服务器、端口、账号和协议选项；
- 加密保存或受文件权限保护的认证信息；
- 可选的节点级 DoH 配置；
- 配置 revision。

节点 ID 用于所有运行映射，不能使用列表序号。netifd 和 Linux 接口名由短 ID 或稳定哈希生成，确保不超过接口名长度限制。

密码不写入日志和诊断包。LuCI 读取节点时不回显密码；密码输入为空表示保持原值，显式操作才清除。

### 4.3 设备与绑定

每个设备保存：

- 稳定内部 ID；
- 规范化 MAC；
- 最近主机名和当前租约 IP；
- 期望固定 IPv4；
- 绑定节点 ID；
- 启用状态和最近出现时间。

同一节点可以被多个设备引用。固定 IP、MAC 和设备 ID 必须唯一。删除节点时，引用它的设备转为未绑定并保持断网，不能自动选择其他节点或主 WAN。

运行状态、当前错误、重试时间和任务进度不频繁写入 flash；它们保存在 `/var/run`、logd 和受限大小的内存环形缓冲中。

## 5. 设备发现与固定地址

系统从 dnsmasq DHCP lease、ubus 和邻居信息发现设备。页面显示主机名、当前 IP、MAC、接入方式和最后在线时间，用户通过列表选择设备和节点。

绑定事务执行以下步骤：

1. 验证设备已经获得可确认的 MAC；
2. 在配置的固定地址池中自动选择地址，或验证用户选择的地址；
3. 检查 UCI、活动租约和邻居表中的冲突；
4. 原子写入设备绑定和 dnsmasq 静态租约；
5. 增加配置 revision 并立即按 MAC 应用策略；
6. 通知设备在下次 DHCP renew 后使用固定地址。

策略不依赖 DHCP renew 才生效。迁移或改地址期间，daemon 可以短期识别当前租约 IP，但最终以 MAC 与固定 IP 的一致映射为准。

设备使用随机 MAC 或更换网卡时会被视为新设备，默认只能访问路由器管理服务。

## 6. 网络隔离与 fail-closed 数据面

### 6.1 二层隔离

GL-MT6000 上采用下列组合：

- 各物理 LAN 口设置 Linux bridge/DSA isolated port，允许到路由器 CPU，不允许 isolated port 之间转发；
- 每个终端 Wi-Fi SSID 启用 `isolate=1`；
- 同桥和跨 radio 场景启用并验证 `bridge_isolate`；
- bridge family nftables 规则作为统一兜底，拒绝普通终端 MAC 之间的转发；
- 不开启可能绕过入站分类的硬件或软件 flow offload，除非后续证明规则语义完全一致。

由于已确认每个物理 LAN 口下没有多终端交换机，端口隔离可以覆盖有线终端互访。若未来改变拓扑，必须使用独立 VLAN 或可管理交换机重新设计。

### 6.2 基础三层拒绝

持久 fw4 配置从开机起执行：

- 拒绝 LAN 普通终端到本地主 WAN 的转发；
- 拒绝未授权 LAN 到任意 PPP、代理 listener 或其他出口；
- 拒绝终端访问其他本地子网、RFC1918、链路本地、组播和广播目标；
- 拒绝客户端 IPv6 转发；
- 拒绝客户端对外 UDP；
- 只允许到路由器自身地址的显式管理白名单。

管理白名单默认包括：

- DHCP；
- 路由器本地 ProxyPool DNS 的 UDP/TCP 53；
- LuCI HTTP/HTTPS 的 TCP 80/443，或用户明确配置的管理端口；
- ARP 等建立 IPv4 局域网通信所必需的链路协议。

SSH 和路由器其他监听服务默认不对白名单终端开放。

### 6.3 MAC 分类与策略标记

bridge ingress 根据源 MAC 把设备映射为内部 policy mark，并把连接代次写入连接跟踪标记。inet 路由和代理链只接受 daemon 当前发布的有效 mark。

同时校验源 IP 与租约映射，异常地址保持断网并记录原因。IP 校验用于防止误配置和普通绕过；MAC 仍不是对恶意仿冒的密码学保护。

daemon 以原子替换 nft set/map 的方式发布新代次。新规则完全准备好之前不开放设备，撤销时先删除授权再停止节点，从而避免更新窗口中的本地 WAN 回退。

### 6.4 按协议的数据路径

未绑定设备：

```text
终端 -> DHCP / 本地 DNS / LuCI
终端 -> 其他目的地：拒绝
```

L2TP：

```text
终端 MAC -> policy mark -> 专用策略路由表 -> 指定 PPP 接口
```

接受规则同时验证 mark 与实际输出接口。PPP 不存在或输出接口不匹配时直接拒绝，不查主路由表作为备用出口。

SOCKS5/SLP：

```text
终端 TCP -> policy mark -> 对应本地透明代理 listener -> 指定远端节点
```

每个节点拥有独立 listener 或等价的不可混淆映射。透明代理只配置为连接指定 SOCKS5/SLP 节点，不能使用 direct/fallback 模式。节点 listener 未就绪时不发布设备授权。

客户端 UDP 在进入上述路径前被拒绝。L2TP daemon 的控制流量以及 SLP 使用 QUIC 时的承载流量，是路由器自身发往已配置节点精确地址/端口的隧道流量，由独立规则允许；这不会给客户端提供 UDP 转发。

### 6.5 在线判定和开放顺序

节点进程存在不等于在线。只有满足全部数据面条件才进入 `online`：

- L2TP：netifd 已上报接口 up、PPP 获得 IPv4、专用路由存在，并通过绑定接口完成 TCP 联网探测；
- SOCKS5：完成 SOCKS5 握手，并通过该代理完成 TCP 联网探测；
- SLP：隧道进程和 listener 正常，并通过该隧道完成 TCP 联网探测；
- 对应 nftables 映射、路由和 DNS 路径已经原子发布。

开放顺序是“启动节点 -> 验证节点 -> 安装路由/DNS -> 发布设备授权”。停止顺序是“撤销设备授权 -> 停止 DNS/路由 -> 停止节点”。

## 7. 按节点 DNS

终端只能把 DNS 发给路由器。外部 DNS 查询不使用运营商 DNS，而由 `proxypoold` 的 DNS 组件按设备 mark 选择节点。

第一阶段统一使用基于 TCP/TLS 的 DoH 上游：

- L2TP 的 DoH socket 绑定到对应 PPP 接口或相同策略 mark；
- SOCKS5 的 DoH TCP/TLS 连接通过对应 SOCKS5 CONNECT 建立；
- SLP 的 DoH TCP/TLS 连接通过对应 SLP 隧道建立；
- 节点未在线或 DoH 验证失败时返回失败，不回退到系统 DNS或主 WAN。

缓存键至少包含节点 ID、查询名、类型和 class，禁止不同节点共享可能暴露位置的缓存结果。节点配置 revision 改变时废弃对应缓存命名空间。

第一阶段对客户端 AAAA 查询返回受控的无 IPv6 结果，并阻止 RA、IPv6 转发和外部 IPv6，避免终端优先尝试不可用或可旁路的 IPv6。

节点服务器域名的 bootstrap 解析属于路由器建立节点所需的控制面流量，不包含客户端访问域名。其来源、结果和失败原因要单独记录，不能与客户端 DNS 缓存混用。

## 8. L2TP 共享架构

### 8.1 结构

正式目标结构为：

```text
proxypoold -> netifd 每节点接口 -> 共享 xl2tpd 多 LAC -> 每节点 PPP 接口
```

xl2tpd 由一个 procd instance 管理并启用 respawn。每个节点拥有独立 netifd 协议配置、PPP options、短接口名、策略路由表和运行状态。

### 8.2 对上游行为的封装

OpenWrt 23.05 的标准 L2TP netifd handler 能通过共享 control socket 增删 LAC，但其 teardown 等待和健康判断不足以满足本项目。`proxypoold` 需要增加：

- 建连 deadline；
- 停止 deadline；
- PPP 有进程但无地址的僵持识别；
- 过期 netifd 事件的 generation 校验；
- 有界清理与必要时的共享 daemon 重建；
- 共享 daemon generation 检测；
- 重启后的分批重拨。

### 8.3 崩溃恢复

共享 xl2tpd 退出时：

1. 立即撤销全部受影响设备的 L2TP 数据面授权；
2. 节点转为 `recovering`，不允许主 WAN 回退；
3. procd 拉起 xl2tpd；
4. daemon 识别新的 xl2tpd generation；
5. 默认每批并行恢复 4 个节点；
6. 每个节点独立进入 online、failed 或 backoff，一个坏节点不阻塞队列。

旧的每节点多实例 xl2tpd 仅在迁移和第一轮真机测试期间保留为工程回退。共享方案通过容量与恢复测试后，正式运行路径不保留双后端自动切换，避免两套实现长期分叉。

## 9. 状态机、任务与重试

### 9.1 节点状态

节点运行状态为：

```text
disabled
queued
starting
validating
online
degraded
stopping
failed
backoff
recovering
```

所有状态转移由 daemon 的单一事件循环或等价的串行协调器提交。耗时 I/O 可以并发执行，但完成结果必须携带 node ID、job ID 和 configuration generation；过期结果直接丢弃。

### 9.2 deadline

初始默认值：

- L2TP 单次建连：60 秒；
- SOCKS5/SLP 单次启动和验证：30 秒；
- 正常停止：10 秒；
- 清理和强制终止：额外有界等待，不能无限循环；
- 健康检查：使用短连接超时，不与用户数据共享无限等待。

具体数值可根据第一轮真机数据调整。无论如何都不允许“接口存在”或“PID 存在”导致无限 connecting。

### 9.3 重试分类

临时错误采用带 jitter 的退避，建议基线为：

```text
5 秒 -> 15 秒 -> 30 秒 -> 60 秒 -> 最长 5 分钟
```

稳定在线一段时间后清零失败计数。WAN 离线时暂停无意义拨号并等待网络事件，WAN 恢复后分批入队。

明确的认证失败、配置缺项或不支持的协议选项标记为配置错误，不做高频自动重试；修改配置或显式重连会产生新 generation 并立即重试。

### 9.4 任务模型

每个写操作返回 job ID。任务记录包括：

- 类型、创建者和创建时间；
- 配置 revision；
- 总数、排队数、运行数、成功数和失败数；
- 每节点当前步骤、尝试次数、deadline 和结构化错误；
- 是否已被新操作取消或替代。

任务进度保存在 daemon 内存和受限环形日志中。浏览器关闭不会取消任务。路由器重启后不伪造旧任务继续运行，而是创建新的系统 reconciliation 任务，把持久期望状态恢复出来。

## 10. 批量导入

批量导入是一个服务端事务，不再由浏览器连续调用几十次启动接口。

流程为：

1. 上传内容受到请求大小和记录数限制；
2. 完整解析当前兼容格式或 V2 导出格式；
3. 规范化字段并检查协议、地址、端口、重复名称、重复 ID 和凭据要求；
4. 检查导入后总节点数不超过 60；
5. dry-run 返回新增、更新、跳过、警告和精确错误行；
6. 有任何阻断错误时不修改 UCI；
7. 用户确认后一次性提交配置 revision；
8. 创建后台 reconciliation job，按协议并发上限启动节点；
9. 页面通过 job ID 查询或订阅进度。

一个节点到达 deadline 只影响自己的结果，队列必须继续。导入成功表示配置已经原子持久化；节点连接结果作为同一任务的后续进度展示，不能让 HTTP 请求保持到所有节点拨号完成。

所有修改型 LuCI 接口改为 POST 并使用现有 LuCI 会话/CSRF 保护；GET 只读。

## 11. LuCI 交互

页面分为三个主要区域。

### 11.1 设备

显示自动发现设备的主机名、MAC、当前 IP、固定 IP、接入方式、绑定节点、节点状态和最后在线时间。用户从列表选择节点完成绑定，不输入 MAC。

### 11.2 节点

显示协议、状态、连接耗时、失败类别、可读错误、尝试次数、下次重试倒计时和绑定设备数。手动重连只创建新 generation，不直接执行脚本。

### 11.3 任务

显示导入、批量启动、系统恢复和删除任务的实时进度。刷新或关闭页面后可以通过 job ID 恢复显示。

常见错误必须区分：认证失败、服务器解析失败、服务器无响应、PPP 未获得地址、代理握手失败、DNS 验证失败、等待 WAN、配置冲突和操作超时。

## 12. 启动、重载与恢复

启动顺序：

1. fw4 持久 fail-closed 基线先于 ProxyPool 服务生效；
2. procd 启动共享 xl2tpd 和 `proxypoold`；
3. daemon 读取 UCI 并验证 schema；
4. 枚举实际 netifd 接口、PPP、子进程、路由和 nftables generation；
5. 清理确认属于 ProxyPool 的陈旧对象；
6. 创建 reconciliation job 并分批达到期望状态；
7. 每个节点验证完成后才开放其设备。

防火墙 reload 后，持久拒绝基线立即存在。daemon 收到事件后重新发布动态 set/map；发布完成前设备保持断网。

daemon 崩溃时 procd 拉起。任何无法证明与当前 generation 一致的运行对象均不获得设备授权。

## 13. 配置迁移与回退

首次启用 V2 时：

- 给现有 `/etc/config/proxypool` 创建带时间和版本的备份；
- 在临时配置中完成解析、转换和完整校验；
- 成功后原子替换，失败则保留 V1 并禁止新 daemon 开放数据面；
- 为旧节点生成稳定 ID；
- 旧绑定若只有 IP，则从当前 DHCP lease 自动匹配 MAC；
- 当时离线且无法确认 MAC 的设备显示为“等待设备出现”，下次 DHCP 接入后自动完成，不要求手工输入；
- 不迁移旧运行路由、防火墙规则、PID 或锁文件。

测试版本提供：

- 刷机前配置备份；
- 可恢复的旧固件/旧包版本；
- V2 到 V1 可读配置导出或明确的恢复步骤；
- 多实例 L2TP 工程回退开关，仅供第一轮验证失败时使用。

回退不允许新旧服务同时运行。回退操作先撤销 V2 动态授权，再停止 V2 服务，然后恢复旧包和配置。

## 14. 可观测性与诊断

daemon 向 logd 输出结构化日志，至少包含 timestamp、level、node ID、job ID、generation、state、attempt、duration 和 error code。高频健康日志采样，避免写 flash 和淹没 logd。

提供一键诊断包，收集：

- 脱敏后的 UCI 配置摘要；
- daemon 和任务状态；
- netifd/PPP/xl2tpd 状态；
- ProxyPool 拥有的路由和规则；
- nftables generation 与计数器；
- DHCP 绑定一致性；
- 最近受限数量的结构化事件；
- 进程、内存和文件句柄统计。

诊断包必须删除密码、密钥、Cookie、LuCI session 和完整认证字段；服务器地址是否脱敏可由用户在导出时选择。

## 15. 分阶段实施

重构按可验证边界交付：

1. 建立自动测试框架、V2 配置模型、daemon 骨架、命令协议和 fail-closed 基线；
2. 实现共享 xl2tpd/netifd L2TP 适配器、状态机、deadline 与分批恢复；
3. 实现设备发现、DHCP 绑定、二层隔离和 L2TP 数据面；
4. 实现 SOCKS5/SLP TCP 适配器和按节点 DNS；
5. 实现事务式批量导入、LuCI 新页面、迁移和诊断；
6. 完成四轮真机验证后删除旧运行路径。

每个阶段都必须保持 fail closed。临时尚未实现的协议可以明确显示“不支持/迁移中”，不能静默走主 WAN。

## 16. 测试策略

### 16.1 自动测试

实现阶段至少覆盖：

- 配置解析、迁移、唯一性和 60 节点边界；
- 状态机的正常、超时、取消、过期事件和重启恢复；
- 退避算法与 WAN 事件；
- 批量导入的全有或全无语义；
- nftables 和策略路由渲染的 golden tests；
- DNS 的按节点选择、缓存隔离和 fail-closed；
- 凭据及诊断脱敏；
- LuCI API 的只读/写入方法和输入限制；
- 模拟 xl2tpd、netifd 和代理进程的故障注入。

CI 构建目标包和固件，并执行 host 单元测试、静态检查和配置渲染测试。硬件特性通过真机测试脚本验证。

### 16.2 第一轮：L2TP 共享架构

依次使用约 5、20、40～50 个真实 L2TP 节点，验证：

- 分批拨号、CPU、内存、进程和接口数量；
- 单个错误账号不阻塞其他节点；
- 节点必须在 deadline 内进入下一明确状态，不能永久 connecting；
- 终止共享 xl2tpd 后自动撤销授权并分批恢复；
- 共享方案相对旧多实例基线没有不可接受的成功率或稳定性退化。

### 16.3 第二轮：隔离与 DNS

覆盖 LAN-LAN、同 Wi-Fi、跨 Wi-Fi、有线-无线、未绑定、已绑定和节点掉线。通过 WAN 侧抓包及 nft 计数器验证：

- 终端互相不可达；
- LuCI、DHCP 和本地 DNS 可用；
- 未绑定和节点掉线设备没有主 WAN 流量；
- 客户端外部 UDP、IPv6、私有网段访问被阻止；
- DNS 请求只通过对应节点；
- 网页和微信文字/图片等基础 TCP 功能正常。

### 16.4 第三轮：批量与故障恢复

使用 40～60 个节点验证正常、错误、重复和超限导入，以及：

- 页面刷新/关闭；
- WAN 断开与恢复；
- 终止 `proxypoold`、共享 xl2tpd 和单节点协议进程；
- 连续保存、重连、停止和删除；
- network/firewall reload；
- 旧任务结果不能覆盖新配置；
- 一个节点失败不能停止任务队列。

### 16.5 第四轮：稳定性与升级

40～50 个常用节点运行 12～24 小时，验证：

- RSS、goroutine、文件句柄和进程数没有持续无界增长；
- 短时 WAN 故障自动恢复；
- 路由器重启后分批恢复；
- GL-MT6000 DSA 端口隔离持续有效；
- 配置备份、恢复和 sysupgrade 后节点及绑定保留；
- 诊断包足以定位失败且不泄露凭据。

## 17. 验收标准

正式替换旧实现必须同时满足：

1. 无论节点失败、daemon/xl2tpd 崩溃、启动中、network reload 或 firewall reload，终端都不能回退到本地主 WAN。
2. 普通终端之间始终不能互访，同时可以访问明确允许的路由器 LuCI 页面。
3. 未绑定设备不能上网；绑定设备只能通过所选节点上网。
4. 客户端外部 UDP 和 IPv6 被阻止，L2TP 控制流量及按配置使用的 SLP QUIC 隧道承载不受误伤。
5. 每次连接都有 deadline、最终状态、错误类别和自动重试策略，不存在永久 connecting。
6. 共享 xl2tpd 崩溃后自动分批恢复，不要求用户逐个手动重连。
7. 批量导入是原子事务；错误行不会产生半套配置；单节点故障不阻塞队列。
8. 节点总数超过 60 时明确拒绝；40～50 节点通过四轮真机测试。
9. 用户不需要输入 MAC；旧 IP 绑定能够自动学习或等待设备再次出现。
10. DNS 按设备绑定的节点发送，节点失效时不回退到运营商 DNS。
11. 配置可迁移、凭据被脱敏，并存在经过验证的安全回退步骤。

## 18. 关键风险与控制

- **共享 xl2tpd 扩大故障域**：procd respawn、generation 检测、先撤授权、分批恢复，并在第一轮与旧多实例基线对比。
- **DSA/无线隔离存在硬件差异**：以 GL-MT6000 真机抓包和端口组合测试作为发布门槛。
- **DoH 上游或节点不兼容**：支持多个可配置上游，逐节点验证并明确报错，禁止 DNS 回退。
- **Go 二进制增加固件体积**：在实施早期建立固件大小预算并使用裁剪构建；不以牺牲状态可靠性为代价退回复杂 Shell 并发。
- **迁移时旧绑定缺少 MAC**：只自动使用可确认 DHCP lease，不猜测；设备下次接入后自动完成。
- **规则更新产生短暂窗口**：基础规则永久拒绝，动态授权使用新 generation 原子发布，永远优先短暂断网而不是短暂直连。

## 19. 已作出的架构决定

- 选择分阶段控制面重构，不继续在现有多脚本并发模型上堆叠补丁。
- 选择 Go 常驻 daemon 作为唯一运行状态所有者。
- 选择 netifd + 单个共享 xl2tpd，配合有界状态机和分批恢复。
- 设备身份自动学习 MAC，并自动创建固定 DHCP 租约。
- 基础网络策略永久 fail closed，未绑定或节点离线时不提供互联网。
- 允许普通终端访问 LuCI，但只开放明确的路由器服务白名单。
- 普通终端在有线和无线场景均执行二层与三层双重隔离。
- SOCKS5/SLP 第一阶段只支持 TCP，客户端外部 UDP 全部阻断。
- DNS 必须按绑定节点传输，不允许使用本地主 WAN 回退。
- 第一阶段仅正式支持 IPv4。
